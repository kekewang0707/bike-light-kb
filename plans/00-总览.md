## 开发顺序与里程碑

```
M1 (数据模型)
 │
 ├──► M2 (爬虫引擎) ───────────────┐
 │                                  │
 ├──► M3 (评价分析) ──► M5 (知识库) ─┼──► M6 (选品看板)
 │                                  │
 └──► M4 (图片分析) ────────────────┘     M7 (内容助手)
                                           │
                                      M8 (定时调度)
```

| 周次 | 完成的模块 | 可演示内容 |
|:---|:---|:---|
| 第1周 | M1 + M2 基础（列表+详情爬虫） | 数据库中有 50+ 商品数据 |
| 第2周 | M2 完整（评价+图片+Pipeline） | 100 商品 + 评价 + 图片全入库 |
| 第3周 | M3（评价分析） + M5（知识库写入） | 评价语义可搜索 |

| 第7-8周 | M8（调度监控） + 全链路优化 | 全自动运行 |

## 风险汇总

| 模块 | 风险 | 应对 |
|:---|:---|:---|
| M2 爬虫 | 京东反爬导致爬虫失效 | 移动端页面优先；Playwright stealth；降低频率；备选：第三方数据API |
| M2 爬虫 | 详情页规格参数提取率低 | 允许 JSONB 存不完整数据；后期人工标注补全 |
| M3 评价分析 | LLM 返回格式不稳定 | response_format: json_object + Pydantic 校验 + 重试 |
| M3 评价分析 | LLM API 成本超预期 | 先跑100条测成本；用 DeepSeek（成本是 GPT-4 的 1/10） |
| M4 图片分析 | Qwen-VL 调用慢/贵 | 仅对主图做多模态描述；详情图只做 OCR |
| M4 图片分析 | CLIP 模型本地运行吃资源 | 用 ViT-B/32（最小模型）；<1000张图片时CPU可接受 |
| M5 知识库 | ChromaDB 单机性能瓶颈 | 初期 <10000 向量，ChromaDB 完全够用；Phase 4 再考虑 Milvus |
| M6/M7 UI | Streamlit 大数据量卡顿 | 数据查询加 @st.cache_data；图表数据预聚合 |
| M8 调度 | 爬虫任务超时 | 设置 30min 超时；下次执行自动恢复 |

## 启动开发的最小路径

1. **`models/base.py` + `models/product.py`** — 搞定数据库连接，能跑通第一条 insert
2. **`crawler/base.py`** — 定义爬虫接口，写死 5 条假数据让 M1 能跑通
3. **`crawler/jd_spider.py` 的 `search()`** — 跑通京东搜索列表抓取，拿到真数据
